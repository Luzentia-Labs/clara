# Project Decisions Log

The canonical, append-only home for load-bearing decisions every later artifact and
delegated agent inherits - both **product** decisions (scope cuts, the answers to the
PRD's open questions) and **implementation conventions** (error-envelope shape, ID scheme,
token strategy, migration style, test harness). One record, two views: an open question
lives in `PRD §Open Questions`; when resolved it is promoted here with a back-link, never
duplicated as free text in both. This block is injected into the handoff context delegated
agents read, so a decision is referenced once, not pasted N times.

| D0001 | npm scope and package names are `@luzentialabs/clara-tokens`, `@luzentialabs/clara-icons`, `@luzentialabs/clara-react`. The CSS custom property prefix stays `--clara-`. | A company scope rather than a common-noun one. Registry search returns zero packages and zero text matches for "luzentia"; `@clara` could not be confirmed free and short common-word scopes are frequently claimed-but-empty. The scope names the publisher, the prefix names the design system. Package names are permanent once published. Promoted from PRD Open Questions. | accepted | -- | 2026-08-21 |
| D0002 | License is MIT. | Standard for design systems (Radix, Chakra, Mantine). Maximum reuse, usable in client work, no adoption friction. Promoted from PRD Open Questions. | accepted | -- | 2026-08-21 |
| D0003 | Behavioural primitive layer is Radix UI, paired with a primitive-isolation rule (PRD Section 4 rule 7). | Mature, proven, largest community; for a solo maintainer proven-and-stable beats actively-churning. The isolation rule keeps `asChild`, `onOpenChange`, and `data-state` out of Clara's public API, so the dependency stays reversible instead of becoming permanent surface. Promoted from PRD Open Questions. | accepted | -- | 2026-08-21 |
| D0004 | Clara's visual identity is decided in F00, a time-boxed foundations pass of 5 working days. Component work begins on day 6 regardless of whether the pass is satisfied. | The ux seat's documented failure mode is refining foundations indefinitely, and that seat explicitly asked to be capped rather than trusted. A deadline held by the document is the cap. F00 blocks F01 and therefore every component. Promoted from PRD Open Questions. | accepted | -- | 2026-08-21 |
| D0005 | All Clara CSS is emitted inside named cascade layers, declared `@layer clara.reset, clara.tokens, clara.components;`. | Unlayered CSS wins over layered CSS regardless of specificity, and a consuming app's stylesheets are unlayered by default, so any consumer rule beats any Clara rule with no `!important` and no specificity contest. This is what makes the Section 4 className contract true. It cannot be retrofitted: introducing layers after v1.0 would silently change the resolved styles of every consumer override already shipped. | accepted | -- | 2026-08-21 |
| D0006 | CSS delivery is one stylesheet per package, deliberately not tree-shaken. The `exports` map enumerates its subpaths and contains no `./*` wildcard. | Simple and robust across bundlers. Forced the v0.1.0 per-component CSS budget to be restated honestly as a fixed stylesheet ceiling (15KB gzipped) plus JS-only per-component budgets, because under a single-stylesheet model no component has a separable CSS cost. The delivery model and every reachable subpath live in the exports map and are permanent once published. | accepted | -- | 2026-08-21 |
| D0007 | Tier 2 (semantic) tokens are public API covered by the breaking-change rule. Tier 1 (primitive) and tier 3 (component) tokens are private and may change in a minor. | Without a declared boundary the distinction is an honour system and consumers settle it for us by overriding tier 3. Enforced mechanically via a generated `tokens.public.json`, with CI failing if the docs site or a published example references a token outside it. | accepted | -- | 2026-08-21 |
| D0008 | `as` is Clara's single polymorphism and composition idiom, used on layout primitives, Button, and overlay triggers. `asChild` is not Clara API. | v0.1.0 carried three idioms answering one question (`asChild` for overlay triggers, `as` for layout primitives, `href` for Button), which broke PRD design principle 2 - "guessable by someone who has used another Clara component" - on paper before any code existed. | accepted | -- | 2026-08-21 |
| D0009 | Package builds use Vite library mode with `vite-plugin-dts`. | Native CSS Modules handling is decisive given the single-stylesheet delivery model (D0006); tsup and unbuild have weak or experimental CSS support and Clara's styling layer is CSS Modules throughout. Shares one tool with Storybook and the reference app. Recorded as TRD ADR-007. | accepted | -- | 2026-08-21 |
| D0010 | Monorepo orchestration is plain pnpm workspaces with scripts. Turborepo is deferred until CI build time is a measured cost. | Three packages and two apps do not yet need a task graph, and no build exists to be slow. Adding Turborepo later is cheap because it is build tooling rather than public API, so the decision stays reversible - unlike the decisions being made alongside it. Recorded as TRD ADR-009. | accepted | -- | 2026-08-21 |
| D0011 | Calendar math for F12 uses `@internationalized/date`. Clara's public props accept and return ISO date strings, not library types. | F12 must document timezone behaviour precisely and operates on calendar dates rather than instants; `date-fns` operates on JS Date, which conflates the two, so it would paper over the exact ambiguity F12 has to resolve. The string boundary keeps the dependency out of Clara's permanent surface. Closes a PRD open question. Recorded as TRD ADR-008. | accepted | -- | 2026-08-21 |
| D0012 | A generated API surface report (`api-extractor` `.api.md` per package) is committed, and CI fails the build on an uncommitted change. | The declared risk class is irreversible distribution; without a surface diff an accidental public API change is discovered by a consumer on install rather than in review. Also enforces the Radix isolation boundary mechanically. The raising seat flagged this as possibly a personal working method promoted to a project requirement; adopted deliberately on the operator's decision. Recorded as TRD ADR-010. | accepted | -- | 2026-08-21 |
| D0013 | Visual regression tooling is Chromatic, consuming the existing Storybook stories. | Built by the Storybook team, so with the PRD's requirement that every component has stories for every state the baseline matrix comes nearly free with no separate driving code. The review interface is the deciding factor at 100+ baselines (components x 2 themes x 2 densities): bulk-approving diffs without looking is the exact failure this gate exists to prevent. Accepts an external service dependency. Closes a PRD open question. | accepted | -- | 2026-08-21 |
| D0014 | Coverage gates are 90% statements AND 85% branches, both blocking. | PRD F22 put its only hard number on statement coverage, which is the metric that can rise while assertions weaken. Branches are where error paths and conditional rendering live, which is where component libraries actually leak, and branch coverage is harder to satisfy vacuously. | accepted | -- | 2026-08-21 |
| D0015 | Mutation testing uses Stryker Mutator over changed files only, with a blocking 70% mutation score. | PRD F22 required a mutation check but named no tool, scope, or threshold and did not say whether it blocked, so the strongest quality signal had no teeth. Changed-file scope keeps the PR path fast; 70% is achievable from day one so the gate is real rather than aspirational, and ratchets as the suite matures. The risk that a threshold gets chosen to be passable rather than meaningful is recorded in the TSD's Known Gaps rather than treated as solved. | accepted | -- | 2026-08-21 |
| D0016 | Manual screen reader verification is VoiceOver/Safari only. NVDA is not performed and is recorded as a stated known gap in the public accessibility statement. | The QA seat scoped NVDA/Firefox for breadth, but NVDA is Windows-only and the maintainer works on macOS, so that half needs a VM or a paid service the project does not have. NVDA and VoiceOver differ in real ways, so this is a genuine gap. Naming it explicitly is the honest option; a blanket WCAG 2.2 AA claim while silently testing one screen reader is exactly the failure the QA seat exists to prevent. Manual keyboard verification remains mandatory for every exported component. | accepted | -- | 2026-08-21 |
| D0017 | `createTheme()` brand ramp generation is deferred to v1.1. | All four seats agreed it was over-promised and proposed four different remedies, which is itself a signal the feature is not well understood. No application needs a brand other than Clara's default; the only consumer today is the maintainer. Deferring dissolves the build-time-vs-runtime question and shrinks the contrast test to the shipped palette. Revival condition: an application requires a non-default brand. Note the amber problem survives independently - `bg-warning-emphasis` is hard in Clara's own palette and is decided in F00. | accepted | -- | 2026-08-21 |
| D0018 | F12 ships DatePicker and DateRangePicker in v1.0; TimePicker moves to v1.1. | Applying the consuming-need test per component rather than to the feature as a whole. Date ranges are common in ERP (reporting periods, filter bars) and F31's list screen consumes one. TimePicker has no named consumer in either reference screen and carries its own 12h/24h, locale, and keyboard model. Revival condition for TimePicker: a screen requires time-of-day entry. | accepted | -- | 2026-08-21 |
| D0019 | Client-side virtualization is cut from F11. Large option sets are served by async option loading, with a documented client-side option-count ceiling. | F15 defers DataGrid on the reasoning that building it badly early is worse than building it properly once an application defines the requirements; F11's 'virtualize 100+ options without breaking aria-activedescendant' is the same class of work in a v1.0 row, so the same reasoning applies. The real ERP answer to a 2,000-account picker is server-side search, which async loading already covers. Also removes the accessibility risk most likely to be subtly broken while passing every automated check. | accepted | -- | 2026-08-21 |
| D0020 | F16 `Menu` (navigation) is deferred to v1.1 alongside F25 AppShell. `DropdownMenu` (actions) remains in v1.0. | DropdownMenu covers what both reference screens need. Navigation Menu belongs with the app shell where navigation actually lives; building it first means guessing at its API, and the two were distinguished only in documentation, which is where consumers pick wrong. | accepted | -- | 2026-08-21 |
| D0021 | A change to a tier 2 token's VALUE (not its name) is a minor release, batched into designated releases and accompanied by a visual changelog entry. A value change that breaks a documented contrast pairing is a bug, not a release. | Literally a value change alters every consuming app's appearance at once, which argues for major; but requiring a major for every neutral-ramp tweak makes the system unusable and no real design system does it. Batching plus a visual changelog gives consumers the warning they need without freezing the palette. Resolves a question that was open in the PRD, the TRD checklist, and the Foundations epic simultaneously. | accepted | -- | 2026-08-21 |
| D0022 | Disabled buttons and controls use `aria-disabled` and REMAIN FOCUSABLE. Native `disabled` is not used where an explanation matters. | Resolves a direct contradiction: F07 permitted a non-focusable disabled button paired with a tooltip, while F13 requires Tooltip to appear on keyboard focus - so the explanation was unreachable by exactly the users who need it. Keeping the control in the tab order means it announces as disabled and its explanation is reachable. In enterprise forms the reason a control is unavailable is often the most important thing on screen. | accepted | -- | 2026-08-21 |
| D0023 | Story granularity is one story per component. | The definition of done is per-component (stories, tests, axe assertion, visual baseline, keyboard pass, docs page, mutation score). A story covering three components carries three times that bar and can never be partially done, so progress would be invisible for long stretches. One story per component makes the DoD and the story boundary the same thing. | accepted | -- | 2026-08-21 |
| D0024 | TDD is used for any component with a documented keyboard interaction table; presentational components are test-after. | Project-specific rule that fits Clara better than the shipped edge-case-count heuristic: the keyboard interaction table IS the specification, so writing its tests before the implementation is natural rather than ceremonial. The boundary is structural and checkable (does this component have a keyboard table?) rather than an estimate made during grooming. | accepted | -- | 2026-08-21 |
| D0025 | v1.0 requires: every must-have feature row Complete, the reference application built on the PUBLISHED package, and the API surface report stable across two consecutive releases with no change. The 1.x support window after 2.0 ships is 6 months, critical and security fixes only. | The PRD said pre-1.0 was unstable but never said what made it 1.0, so 1.0 would have been declared by feel. API stability across two releases is the criterion that actually proves the surface has settled, which is the whole meaning of 1.0 for a library. The support window is stated because consumers running three applications need to know where they stand before they upgrade. | accepted | -- | 2026-08-21 |
| D0026 | F27-F30 (command palette, filter builder, charts, Tailwind preset) move out of the Feature Inventory into a Future Considerations section, each with a revival condition. | A Nice-to-have with no version and no revival condition is a component waiting for someone to feel like building it, and it makes the inventory read as a list of commitments when it is not. Moving them preserves the reasoning without the rows implying a plan. | accepted | -- | 2026-08-21 |
| D0027 | Docs site and Storybook are hosted on GitHub Pages. | Keeps everything on one platform with no additional account or service, and is trivially movable later since static hosting is not public API. Preview deploys per PR would be nicer on Vercel; not worth an external dependency at this stage. | accepted | -- | 2026-08-21 |
| D0028 | `clara-tokens` is built with Style Dictionary plus `tsc`, not a Vite build. | The package emits no components and no CSS Modules, so the reason Vite was chosen for the other two packages does not apply. A simpler pipeline means less build surface to maintain. `clara-icons` and `clara-react` remain on Vite library mode (D0009). | accepted | -- | 2026-08-21 |

## Notes

- Decisions are numbered globally and zero-padded: `D{NNNN}`.
- Append with `scripts/decisions.py add`; list with `scripts/decisions.py list`.
- `Status`: `accepted` | `superseded` | `revisited`. A superseding decision names the one
  it replaces in `Supersedes`.
- Distinct from the sprint per-tranche ledger (`scripts/ledger.py`), which is scoped to
  a single delivery run; this is the durable project spine.
